# Jira Issue Integration

`worktree` can derive branch names directly from Jira issues in your Jira workspace.

## Basic Usage

```bash
worktree branch --jira DEV-123
worktree branch --jira dev-123
```

The generated branch name is shown as the default in the prompt, so you can accept it or edit it before creation.

## How Branch Names Are Built

1. Read issue type and summary from the Jira API.
2. Sanitize the summary into a branch-safe slug, cut to at most 48 characters at the last dash so it ends on a whole word. A single word longer than 48 characters is cut at 48.
3. Optionally prepend a configured prefix based on issue type.

For example, a bug DEV-123 titled "Login redirect loops forever when the session cookie expires during checkout"
becomes `fix/DEV-123-login-redirect-loops-forever-when-the-session` with `branchPrefix.bugfix` set to `fix/`.

Supported issue-type prefix mapping:

- `Feature`, `Story`, and other non-bug/chore types -> `branchPrefix.feature`
- `Bug` -> `branchPrefix.bugfix`
- `Task` -> `branchPrefix.chore`

If a prefix key is not configured, no prefix is applied.

This built-in mapping applies **only when no rules are set**. If `.worktree.yml` has a `jira.branchType`
list (or a shared top-level `branchType` list, which `jira.branchType` wins over), the rules decide the kind instead and the mapping above is not consulted: an issue no rule matches
gets no prefix unless the list ends with `- otherwise: <kind>`. See
[Branch-type rules](/docs/project-configuration#branch-type-rules) for the syntax, and for why to name
fields and options by id. A shared list can name the issue type as `Type`, which Jira answers beside `issuetype`.

## Assigning the issue

`--assign` assigns the Jira issue to the account behind `jira.email` while the branch is created, and
`--no-assign` skips it for one run. With neither, `jira.autoAssign` decides: `true` always assigns, `false`
never does, and unset asks once and saves your answer. A non-interactive run (`--json`, `--yes`, CI) with the
key unset assigns and saves nothing. This key is separate from `github.autoAssign`.

```bash
worktree branch --jira DEV-123 --assign
worktree branch --jira DEV-123 --no-assign
worktree config jira.autoAssign true
```

- **An issue someone else holds is never reassigned.** Jira keeps one assignee, so writing yours would remove
  a colleague who may be working it. `worktree` warns with their name, leaves the issue as it is and creates the
  branch; `--assign` does not override this. An issue already assigned to you is reported as such and nothing
  is written. In the `--json` document, `assigned` is `true` when the issue is assigned now or was already
  yours, and `false` when someone else holds it.
- **The account needs the *Browse Projects* and *Assign Issues* permissions** on the issue's project. Without
  them, or when the issue is not found or Jira does not accept the account, `worktree` warns with what Jira
  said.
- **A failed assignment never stops the branch.** The worktree is created either way, and `assigned` is `false`.
- The assignment happens before the worktree is created, so a prompt is never buried behind creation output.

## Moving the issue to in progress

`--start` moves the Jira issue to its in-progress status once the worktree exists, and `--no-start` skips it for
that one run. Without either, [`jira.autoStart`](/docs/configuration#jira-integration-notes) decides: `true` moves,
`false` never does, and unset asks once in a terminal and saves the answer under that key. **A non-interactive run
with the key unset moves the issue** and saves nothing, so pass `--no-start` or set the key to `false` if a script
that passes `--jira` must not change an issue's status. The full order and where it sits in a run are in the
[branch command](/docs/commands/branch#moving-the-jira-issue-to-in-progress).

```bash
worktree branch --jira DEV-123 --start
worktree branch --jira DEV-123 --no-start
worktree config jira.autoStart true
```

Jira workflows are per project and the statuses are renamed and translated freely, so nothing is matched by name.
Jira groups every status into a category (To Do, In Progress, Done), and `worktree` goes by that. Up to three
requests follow, each cut off after 15 seconds: the issue's status, the transitions Jira offers from it, and the
transition itself.

- An issue in the To Do category moves through the transition that leads to an in-progress status. When the
  workflow offers several transitions that lead to the same status, the first is used.
- An issue already in the In Progress category is not moved, and the document's `started` is `true`. That costs
  one request.
- An issue in the Done category, or in any other category, is left alone with a warning and `started` is `false`.
- When the available transitions lead to more than one in-progress status, `worktree` does not guess which is
  "in progress" and writes nothing. The warning lists the statuses, `started` is `false`, and you move it in Jira.
- When Jira offers no in-progress transition, the warning says so and `started` is `false`. Jira answers with an
  empty list both when the workflow has no such transition and when the account lacks the permission, so the
  warning names both causes.
- A transition whose screen has a required field is refused by Jira. The warning names the transition and says it
  may need a field set in Jira, `started` is `false` and nothing changes.
- Only the status changes: no assignee, comment or field is written. `--assign` and `--start` are separate
  requests, and one failing does not affect the other.
- **The account needs the *Browse Projects* and *Transition Issues* permissions** on the issue's project. A failed
  move never stops the branch: the worktree is created either way, the warning appears in `warnings`, and the exit
  code is unaffected.
- The move happens after the worktree exists, before the env files, the install and the opener, and never when
  reopening an existing worktree. A dry run ignores `--start` and asks nothing.

## Authentication Resolution

Authentication is resolved in this order:

1. Existing `jira.host`, `jira.email`, and `jira.apiToken` in git config. `jira.host` is read from git config, else from the team's `.worktree.yml`, with no prompt; a file's host receives everyone's credentials, see [Project Configuration](/docs/project-configuration#jirahost-receives-everyones-credentials).
2. Interactive prompts for missing values, then save to local git config.

## Suggested Setup

```bash
worktree config jira.host https://your-domain.atlassian.net
worktree config jira.email your-email@example.com
worktree config jira.apiToken <api-token>
worktree config branchPrefix.feature feature/
worktree config branchPrefix.bugfix fix/
worktree config branchPrefix.chore chore/
```

You can also configure only missing values:

```bash
worktree config --missing --names jira.host,jira.email,jira.apiToken,branchPrefix.feature,branchPrefix.bugfix,branchPrefix.chore
```

An empty answer to the token prompt keeps the token already stored rather than clearing it.

## Getting a Jira API Token

1. Visit [Atlassian Account Settings](https://id.atlassian.com/manage-profile/security/api-tokens)
2. Click "Create API token"
3. Copy the generated token and use it with `worktree config jira.apiToken`

The token is stored locally in git config and never sent anywhere except to your Jira instance.
